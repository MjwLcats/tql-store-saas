## 1. 已确认的架构决策

本文档以以下决策为准，后续开发不得再沿用旧文档中的 React、Docker Compose 或旧目录名称。

1. 根目录只保留当前三个项目目录和 `docs`：
   - `tql-store-admin`：后端项目，包含 Java Spring Cloud 服务以及后端相关的 Python 预测服务。
   - `tql-store-web`：PC 前端项目，采用 pnpm workspace，同时承载平台端和商家端两个独立应用。
   - `tql-store-app`：移动端项目，使用 HBuilderX 创建和运行的 uni-app Vue 3 项目。
   - `docs`：项目设计、开发与运维文档。
2. PC 端统一使用 Arco Design Pro Vue 3，不使用 React 版本。
3. 平台端和商家端分别启动、构建和部署，但共享请求、权限、类型、工具和业务组件。
4. 后端第一阶段仍拆分为多个 Spring Cloud 服务。
5. MySQL、Redis、Nacos、RocketMQ、MinIO 等中间件使用本机现有环境，不提供 Docker Compose。
6. Java 后端服务从 IDEA 启动，PC 前端从 WebStorm 启动，移动端从 HBuilderX 启动。
7. 系统统一使用 `tql-store` 作为工程和服务命名前缀，数据库固定命名为 `tql_store_saas`。

## 2. 项目目标和范围

第一阶段只搭建可持续开发的工程骨架，不开发完整业务功能。

需要完成：

1. Spring Cloud 多服务后端框架。
2. SaaS 多租户、用户上下文和权限基础结构。
3. Arco Design Pro Vue 3 平台端和商家端框架。
4. uni-app Vue 3 移动端框架。
5. Python 预测服务基础框架。
6. AI、外部接口集成、文件、消息和定时任务服务框架。
7. RocketMQ 事件模型和基础封装。
8. IDEA、WebStorm、HBuilderX 本地启动规范。
9. 统一代码、配置、数据库、服务和包命名规范。

第一阶段不做：

1. 完整巡检、培训、勋章和预测业务。
2. 正式预测算法和复杂报表。
3. Kubernetes、Docker Compose 和生产部署脚本。
4. 高并发压测。
5. 最终品牌视觉稿，但 PC 页面必须遵守 Arco Design Pro 规范。

## 4. 统一命名规范

### 4.1 总体规则

| 对象 | 规则 | 示例 |
|---|---|---|
| 项目目录 | kebab-case，统一 `tql-store` 前缀 | `tql-store-admin` |
| Maven artifactId | kebab-case，统一 `tql-store` 前缀 | `tql-store-system` |
| Nacos 服务名 | 与 Maven artifactId 一致 | `tql-store-system` |
| Java 包名 | 全小写 | `com.tql.store.system` |
| npm scope | `@tql-store` | `@tql-store/api` |
| Vue 文件 | PascalCase | `TenantSelector.vue` |
| TS 文件 | kebab-case 或约定功能名 | `request.ts`、`permission.ts` |
| 数据库 | snake_case | `tql_store_saas` |
| 数据表 | snake_case，按业务域前缀 | `sys_merchant_user`、`ops_task` |
| 数据库字段 | snake_case | `tenant_id`、`create_time` |
| 环境变量 | UPPER_SNAKE_CASE | `VITE_API_BASE_URL` |
| MQ Topic | 小写点分业务域 | `forecast.requested` |

### 4.2 禁止混用的名称

以下名称不得继续出现在新代码和新配置中：

```text
tql_saas
tql-saas-store-ops
backend
admin-web
mobile-uniapp
ADMIN（作为通用 PC 客户端类型）
com.tongqinglou（新代码包名）
```

统一替换为：

```text
数据库：tql_store_saas
系统前缀：tql-store
Java 根包：com.tql.store
平台端客户端类型：PLATFORM
商家端客户端类型：MERCHANT
移动端客户端类型：MOBILE
```

### 4.3 数据库与表命名

第一阶段所有服务共用数据库：

```sql
CREATE DATABASE tql_store_saas
  DEFAULT CHARACTER SET utf8mb4
  DEFAULT COLLATE utf8mb4_0900_ai_ci;
```

业务域表前缀建议：

| 业务域 | 表前缀 | 示例 |
|---|---|---|
| 系统与权限 | `sys_` | `sys_platform_user`、`sys_merchant_user` |
| 门店运营 | `ops_` | `ops_inspection_task` |
| 培训勋章 | `train_` | `train_badge_record` |
| 预测 | `forecast_` | `forecast_task` |
| AI | `ai_` | `ai_call_log` |
| 外部集成 | `integration_` | `integration_api_log` |
| 文件 | `file_` | `file_object` |
| 消息 | `message_` | `message_notice` |

第三方数据镜像统一使用 `integration_{provider}_{entity}`，其中 provider 使用稳定、简短的小写标识，例如哗啦啦使用 `hll`：

- 哗啦啦门店镜像：`integration_hll_shop`
- 哗啦啦门店与本地门店映射：`integration_hll_store_mapping`
- 人力管家简称固定为 `rlgj`，组织、职位、岗位、用户镜像分别使用 `integration_rlgj_organization`、`integration_rlgj_position`、`integration_rlgj_post`、`integration_rlgj_user`
- 本地统一门店主数据：`sys_store`
- 明细表追加 `_item`，映射表追加 `_mapping`，历史表追加 `_history`
- 不使用含义不明确的 `inf_`、`tb_`、`t_`、`biz_` 前缀

第三方镜像表必须保留第三方主键、`tenant_id`、最后同步任务、最后同步时间和原始 JSON；以 `(tenant_id, 第三方主键)` 建立唯一键，通过幂等 upsert 更新，禁止直接把第三方主键作为本地主键。

平台端和商家端的组织、用户主数据必须明确分表：

- 平台端：`sys_platform_organization`、`sys_platform_user`
- 商家端：`sys_merchant_organization`、`sys_merchant_user`
- 第三方镜像只保存来源系统事实数据，本地 `sys_*` 表保存可参与业务和权限计算的主数据
- 人力管家组织、用户只投影到商家端表，不允许写入平台端表
- 人力管家员工默认 `login_enabled=0`，同步员工目录不等于开通系统登录权限
- 认证、个人中心、菜单、RBAC 和业务数据权限必须直接使用端侧用户表，禁止再访问历史统一用户表
- 历史 `sys_user`、`sys_user_role`、`sys_user_store` 已归档为对应的 `_legacy` 表，仅用于迁移审计，不参与任何运行时查询或写入

### 4.4 数据库中文注释强制规范

数据库表注释和字段注释属于数据库设计的一部分，必须与表结构同时设计、同时评审、同时交付，具体要求如下：

1. 每个 `CREATE TABLE` 必须使用 `COMMENT='完整中文表说明'`，说明该表存储的业务对象或用途。
2. 每个字段都必须使用 `COMMENT '完整中文字段说明'`，包括主键、外键、关联表字段、审计字段和逻辑删除字段，不能只给业务字段写注释。
3. 状态、类型、范围等枚举字段必须在注释中说明主要取值及中文含义，例如：`状态：0停用，1启用`。
4. 禁止空注释、`?`/`???`、`TODO`、`待补充`、复制字段名作为注释，以及含义不明确的“标志”“状态”等单独描述。
5. SQL 文件统一保存为 UTF-8，文件开头执行 `SET NAMES utf8mb4;`，MySQL 客户端必须指定 `--default-character-set=utf8mb4`。
6. Windows 环境禁止通过 `Get-Content ... | mysql` 管道执行包含中文的 SQL；PowerShell 可能在管道中转换字符编码，导致中文注释永久写成问号。必须使用 MySQL 客户端的 `source` 命令直接读取 SQL 文件。

标准执行方式：

```powershell
mysql --host=127.0.0.1 --port=3306 --user=root --password=123456 `
  --default-character-set=utf8mb4 `
  --execute="source D:/Project/tql-store-saas/tql-store-admin/sql/migration/Vxxx__description.sql"
```

每次创建表或执行迁移后，必须运行以下验收 SQL；两个查询结果都必须为 `0`：

项目已提供 `tql-store-admin/sql/check/validate_database_comments.sql`，可直接通过 MySQL `source` 执行。

```sql
SELECT COUNT(*) AS invalid_table_comments
FROM information_schema.TABLES
WHERE TABLE_SCHEMA = 'tql_store_saas'
  AND (TRIM(TABLE_COMMENT) = '' OR TABLE_COMMENT LIKE '%?%');

SELECT COUNT(*) AS invalid_column_comments
FROM information_schema.COLUMNS
WHERE TABLE_SCHEMA = 'tql_store_saas'
  AND (TRIM(COLUMN_COMMENT) = '' OR COLUMN_COMMENT LIKE '%?%');
```

代码评审时，任何表或字段缺少完整中文注释，数据库迁移均视为未完成，不允许合并或交付。

除平台级全局表外，租户业务表必须包含：

```text
tenant_id
create_by
create_time
update_by
update_time
deleted
```

## 7. SaaS 多租户和权限

### 7.1 客户端类型

请求头统一为：

```text
Authorization: Bearer <token>
X-Tenant-Id: <tenantId>
X-Client-Type: PLATFORM | MERCHANT | MOBILE
X-Store-Id: <storeId，可选>
```

规则：

1. `PLATFORM`：平台运营人员使用；切换目标租户必须具备平台权限并记录审计日志。
2. `MERCHANT`：商家总部或门店 PC 用户使用；租户必须来自登录身份，不能通过修改 Header 越权切换。
3. `MOBILE`：移动端用户使用；租户和可操作门店由 Token 与用户关系确定。
4. 后端不能只相信 `X-Tenant-Id`，必须与 Token、用户权限和客户端类型联合校验。

### 7.2 租户上下文

租户解析顺序：

```text
1. 验证 Token 并解析登录身份
2. 根据 X-Client-Type 确认客户端权限边界
3. 校验 X-Tenant-Id 是否允许访问
4. 写入 TenantContext
5. 业务结束后在 finally 中清理上下文
```

异步任务、线程池和 MQ 消费不得直接依赖 Web 请求的 ThreadLocal，必须显式传递 `tenantId`。

### 7.3 权限层级

```text
租户套餐/模块权限
菜单权限
按钮权限
```

### 7.4 RBAC 用户、角色与门店数据权限（已落地）

平台端和商家端采用独立用户及关联表：

```text
sys_platform_user ──< sys_platform_user_role >── sys_role
                                                   └──< sys_role_menu >── sys_menu

sys_merchant_user ──< sys_merchant_user_role >── sys_role
    │                                              └──< sys_role_menu >── sys_menu
    ├── organization_id → sys_merchant_organization（所属组织）
    ├── primary_store_id → sys_store（所属主门店）
    ├── data_scope（数据权限类型）
    └──< sys_merchant_user_store >── sys_store（授权门店集合）
```

约束：

1. 平台端用户存放于 `sys_platform_user`；平台角色固定归属 `tenant_id = 0`、`client_type = PLATFORM`。
2. 商家端用户、角色和门店必须归属当前登录租户，接口不得接收可覆盖租户的请求参数。
3. 商家员工和登录账号统一存放于 `sys_merchant_user`，`login_enabled=0` 表示仅为人员档案，不能登录且不要求配置角色和门店权限。
4. 开通商家登录时必须设置账号、密码、角色和所属主门店，可以额外关联多个授权门店。
5. `CUSTOM` 数据权限以 `sys_merchant_user_store` 中的授权门店集合为准。
6. `STORE` 使用所属主门店，`STORE_AND_CHILD` 使用主门店及其下级门店，`SELF` 只允许访问本人创建的数据。
7. 业务服务必须根据 `X-User-Id` 和 `X-Client-Type` 回查对应端侧用户表中的最新用户状态、登录权限、主门店和数据权限，不能只相信请求头中的数据范围。
8. 用户或角色停用后，不再返回其菜单；后端管理接口也必须校验角色菜单权限。

2. 403 显示无权限反馈。
3. 业务错误统一使用 Arco Message 或 Notification。
4. 保留后端 `traceId`，方便问题排查。
5. 文件流、分页和普通对象使用明确的 TypeScript 类型。

## 9. Arco Design Pro Vue 开发规范

### 9.2 页面结构

标准列表页建议结构：

```text

├── 数据表格 Card
│   ├── 工具栏
│   ├── Table
│   └── Pagination
```

使用规则：

- 简单编辑使用 `Modal`，信息较多或需要连续编辑时使用 `Drawer`。

#### 11.3.1 人力管家同步

人力管家接口统一使用 POST 表单请求，公共参数为 `corp_name`、`app_id`、10 位秒级 `timestamp` 和 `token`。签名规则为：

```text

```

拼接顺序不得调整，`app_secret` 只能通过 `HR_BUTLER_APP_SECRET` 环境变量提供，禁止写入源码、`application.yml`、SQL、日志或同步任务明细。

当前同步接口与任务类型：

| 任务类型 | 人力管家接口 | 落库范围 |
|---|---|---|
| `ORGANIZATION` | `/api/org/list` | 组织镜像及 `sys_merchant_organization` |
| `POSITION` | `/api/position/list`、`/api/post/list` | 职位、岗位镜像；岗位接口按有效组织并发查询 |
| `USER` | `/api/user/simplelist` | 用户镜像及 `sys_merchant_user` |

接口没有提供可靠的增量游标，因此 PC 端默认使用 `FULL` 全量快照同步；全量任务完成后，将本次快照不存在的数据标记为逻辑删除。所有写入使用租户与第三方主键组成的唯一键执行幂等 upsert。

用户接口可能返回证件号、银行卡号、出生日期和扩展字段。当前系统只保存组织关系、工号、姓名、联系方式、职位、岗位、职级和在离职状态；`user_id_card`、`bank_card`、`extValueMap` 等敏感字段不得落库，用户镜像中的 `raw_json` 也必须先执行字段白名单筛选。

## 16. 第一阶段验收标准

1. 根目录只使用 `tql-store-admin`、`tql-store-web`、`tql-store-app` 和 `docs`。
2. 数据库统一为 `tql_store_saas`，配置中无旧数据库名。
3. Java artifactId、Nacos 服务名和包名符合统一规范。
4. 所有后端服务可从 IDEA 使用 `dev` 配置启动并注册到 Nacos。
5. 网关可访问 auth、system 等基础服务。
6. 平台端和商家端均基于 Arco Design Pro Vue 3。
7. 两个 PC 应用可从 WebStorm 分别启动和构建。
8. 两端没有跨应用源码引用，共享代码均来自 `packages/*`。
9. PC 页面没有混入其他基础 UI 组件库。
10. 登录、菜单、按钮和字段权限骨架可运行。
11. `tql-store-app` 可从 HBuilderX 运行，并已移除默认演示内容。
12. Python `/health` 可访问。
13. 租户 ID 不仅从 Header 读取，还会结合 Token 和客户端类型校验。
14. 本地开发不依赖 Docker。
15. README 中分别提供 IDEA、WebStorm、HBuilderX 和 Python 启动说明。
16. 仓库中不包含密码、密钥、构建产物和 IDE 私有文件。

## 17. 开发注意事项

1. 第一阶段优先保证边界、命名、配置和启动流程正确。
2. 平台端、商家端和移动端是三个客户端，权限边界不可混用。
3. PC 端必须以 Arco Design Pro Vue 3 为基础，不自行另建一套布局和视觉规范。
4. 共享包只放真正跨应用稳定复用的代码，避免过早抽象全部业务。
5. 租户隔离、数据权限和字段权限必须由后端兜底。
6. 所有外部系统调用进入 `tql-store-integration`。
7. 所有大模型调用进入 `tql-store-ai`。
8. Python 预测代码保留为独立服务，不嵌入 Java 进程。
9. MQ 消息必须显式携带 tenantId、messageId 和 traceId。
10. 任何新增模块都应先检查命名是否符合本文件第 4 节。
